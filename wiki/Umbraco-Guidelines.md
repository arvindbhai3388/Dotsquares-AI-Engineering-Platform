# Umbraco Guidelines

Guidance for content modeling, custom development, upgrades, and performance on Umbraco CMS projects. Umbraco sits partly in the presentation layer and partly as a content-management application layer — see [Architecture Overview](Architecture-Overview.md).

## Content modeling

- Model content types around **editorial intent**, not database convenience. A `BlogPost` content type should map to how an editor thinks about a blog post, not to whatever shape happens to be easiest to query.
- Use **Compositions** to share common property groups (e.g., "SEO Metadata," "Open Graph") across unrelated content types instead of duplicating the same properties on each type. Compositions are Umbraco's equivalent of interfaces/mixins for content types — treat them with the same DRY discipline as C# interfaces.
- Prefer **Element Types** (content types marked "is an Element type") for nested/repeatable structured data inside a Block List or Block Grid editor (e.g., a "Call to Action" block), rather than free-text rich text areas that bury structured data inside HTML.
- Use strongly-typed models generated by **Umbraco ModelsBuilder** (or hand-written models implementing `PublishedContentModel` if ModelsBuilder isn't in use on a given project) in Razor views — never access `IPublishedContent.Value<T>("propertyAlias")` by magic string alias throughout view code; centralize the alias-to-property mapping in the generated/hand-written model instead. Magic strings scattered across views mean a renamed property alias silently breaks views at runtime instead of failing at compile time.
- Keep the content tree shallow enough for editors to navigate without training — deeply nested trees (5+ levels) are usually a sign that content structure is being used to express navigation/categorization that should instead be tags, a picker, or a dedicated taxonomy content type.
- Document every custom content type's intended use in its description field in the backoffice — this is the first thing another developer or an editor checks, and it costs nothing to keep current.

## Custom property editors

- Only build a custom property editor (a full Umbraco Package UI component) when the built-in property editors (Content Picker, Media Picker, Block List, Multi-URL Picker, Tags, Dropdown, etc.) genuinely cannot express the requirement — a custom editor is a maintenance burden that must be carried through every future Umbraco upgrade.
- Modern Umbraco (v10+, backoffice on Lit/web components) property editors are registered as Umbraco packages with a manifest (`umbraco-package.json`) rather than AngularJS controllers (the pre-v10 pattern) — check the target Umbraco major version before following older tutorials that assume the AngularJS backoffice.
- A custom property editor's stored value (in the `umbracoPropertyData` table, as JSON in modern Umbraco) must be **versionable and migratable** — plan for what happens to existing content when the editor's data shape changes in a later release, the same way you'd plan an EF Core migration (see [EF Core Guidelines](EFCore-Guidelines.md) for the expand/contract mindset, which applies here too).
- Validate custom editor values server-side as well as in the backoffice UI — the backoffice UI validation is a content-editor convenience, not a security boundary; a malicious or malformed API request to the backoffice's management API must still be rejected server-side.

## Safe upgrade practices

- Umbraco major versions (e.g., 8 → 9, 9 → 10+) are **not always in-place upgrades** — 8 → 9+ was a full platform migration (.NET Framework → .NET / ASP.NET Core) requiring the Umbraco migration/Deploy tooling or a content-and-schema migration project, not a NuGet package bump. Treat a major-version jump as its own project with its own [Propose](AI-Workflow-Discipline.md) step, never as an incidental part of an unrelated feature ticket.
- Within a major version, apply **minor/patch upgrades regularly** rather than batching years of updates — Umbraco's own upgrade path is only reliably tested version-to-version, not from a three-year-old minor to the latest.
- Before any upgrade: take a full database backup and a media folder backup, note the current package versions of any third-party Umbraco packages in use (they may not support the target version yet), and run the upgrade against a non-production environment first with a real content copy, not a fresh empty site.
- After an upgrade, verify: content renders correctly across each content type actually in use (not just the homepage), the backoffice loads and custom property editors still function, and any custom Examine/search indexes rebuild successfully.
- Never edit generated ModelsBuilder files by hand — they are regenerated and hand edits will be silently lost.

## Performance

### Output caching

- Umbraco's built-in output caching should be enabled for genuinely public, non-personalized pages — but be precise about what "personalized" means: even a page with per-visitor content (e.g., a logged-in user's name in the header) cannot use a single shared cache entry without variation by that state (via cache vary-by-cookie/header, or by excluding just that fragment from the cache via `<cache>` tag helper boundaries or a child action, rather than disabling caching for the whole page).
- Cache expensive, page-independent lookups (navigation trees, footer content, global settings singletons) with `IAppPolicyCache`/`IMemoryCache`, invalidated via Umbraco's content-cache-refresher notifications (`ContentCacheRefresher`, or the newer `INotificationHandler<ContentCacheRefresherNotification>` in modern Umbraco) rather than a fixed TTL that risks serving stale content after an editor publishes a change, or re-querying the content cache on every request.
- Be careful with output caching and A/B testing, personalization, or query-string-driven variants (`?utm_source=...`) — vary the cache key correctly or disable caching for those routes, since a naive full-page cache can leak one visitor's variant to another.

### Content picker pitfalls

- **N+1 via pickers**: iterating a list of content nodes and resolving a Content Picker or Media Picker property on each one individually (`item.Value<IPublishedContent>("relatedItem")`) triggers a content-cache lookup per item. On the in-memory NuCache this is cheap but not free at scale (hundreds of items per page); on older/legacy Umbraco XML cache implementations it is considerably more expensive. Batch-resolve where the API allows it, or restructure the query to avoid resolving pickers inside a large loop rendered per-request.
- **Broken/unpublished picker references**: a Content Picker can point to a node that has since been unpublished, moved to the trash, or had its permissions changed — `Value<IPublishedContent>(...)` returns `null` in these cases. Every picker access in a view must null-check before use; a missing null-check is one of the most common causes of production 500s on Umbraco sites after routine content maintenance.
- **Multi-Node Tree Picker / Multi-URL Picker returning stale/broken links**: the same null-safety applies when resolving each picked item — filter out nulls before rendering a list, rather than letting one broken reference blank the whole component.
- Avoid deeply chained picker traversals in views (`Value<IPublishedContent>("a").Value<IPublishedContent>("b").Value<IPublishedContent>("c")...`) — each hop is a further null-check burden and a further cache lookup; if a view needs data three hops away from its own content node, consider whether that data should instead live closer (via a Composition) or be resolved once in a view component/controller rather than repeatedly in markup.
