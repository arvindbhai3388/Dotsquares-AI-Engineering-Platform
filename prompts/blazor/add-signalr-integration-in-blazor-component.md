# Integrate a SignalR Hub Connection into a Component's Lifecycle

**Category:** Blazor
**Use when:** A component needs real-time push updates from a SignalR hub independent of Blazor Server's own internal circuit connection.

## Prompt

Before implementing, clarify this SignalR connection is separate from Blazor Server's own SignalR circuit (if applicable) — a component-level `HubConnection` is an additional client connection the component opens itself to a specific application hub, and running this inside a Blazor Server app means two SignalR connections are now active per user, which has real resource implications at scale; confirm with me whether a shared, DI-scoped `HubConnection` (one per circuit, injected into whichever components need it) is more appropriate than each component opening its own.

Build the `HubConnection` via `HubConnectionBuilder().WithUrl(NavigationManager.ToAbsoluteUri("/yourhub"), options => { ... }).WithAutomaticReconnect().Build()` — always include `WithAutomaticReconnect()` unless there's a specific reason not to, since a dropped connection with no reconnect policy leaves the component silently stale with no error surfaced to the user. Register message handlers with `hubConnection.On<T>("MethodName", payload => { ... })` before calling `StartAsync()`, not after, to avoid a race where the server could send a message before the client is listening.

Every handler registered via `.On<T>(...)` runs outside Blazor's rendering synchronization context, so any handler that touches component state and expects a re-render must call `await InvokeAsync(StateHasChanged)`, not a bare `StateHasChanged()` — forgetting `InvokeAsync` here is one of the most common Blazor Server bugs and can throw or silently fail to update the UI depending on timing. Wire up `hubConnection.Reconnecting`, `Reconnected`, and `Closed` handlers to update a connection-status indicator in the UI so users understand when real-time data may be stale.

Start the connection in `OnInitializedAsync` (or `OnAfterRenderAsync(firstRender)` if it must happen after first render for interop-adjacent reasons), and implement `IAsyncDisposable` to call `await hubConnection.DisposeAsync()` when the component is torn down — a component that opens a `HubConnection` and never disposes it leaks an open connection for the lifetime of the server process or until the client's circuit itself is torn down, and under Blazor Server this multiplies per active user. Guard all handler bodies against operating on a disposed/unmounted component (check a cancellation flag set in `DisposeAsync`) since a message can arrive in the brief window between navigation away and disposal completing. Add integration-style tests around the hub contract if this codebase has any SignalR test infrastructure already, and at minimum a bUnit test verifying the component renders the correct status text for each connection state transition, using a fake/mocked connection abstraction rather than a real `HubConnection`.
