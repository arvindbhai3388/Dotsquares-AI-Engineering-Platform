# Add or Fix Server Prerendering Support for a Component

**Category:** Blazor
**Use when:** A component throws or renders incorrectly on first load because it assumes JS interop or full interactivity is already available.

## Prompt

Before fixing anything, reproduce the failure and identify exactly which call is failing during prerendering — this is almost always either an `IJSRuntime` call made from `OnInitialized[Async]`/`OnParametersSet[Async]` (prerendering runs these lifecycle methods server-side with no browser attached, so any JS call throws `InvalidOperationException: JavaScript interop calls cannot be issued during server-side prerendering`), or code that assumes a fully-formed `NavigationManager` URI, or a service that behaves differently/throws when there's no live circuit yet. Report the exact failing call and its lifecycle stage before proposing a fix.

The correct fix is almost never "wrap it in try/catch and swallow the exception" — that hides real interop failures too. Instead, move any JS-dependent logic out of `OnInitialized[Async]`/`OnParametersSet[Async]` and into `OnAfterRenderAsync(firstRender)`, which only runs after the component has an actual render surface (post-prerender in Server; after first real render in WASM) — this is the one lifecycle method Blazor guarantees is safe for interop. If data needs to be ready by the time the JS call happens, fetch it in `OnInitializedAsync` (server-renderable, no interop) and only perform the interop-dependent step in `OnAfterRenderAsync`.

For components that must render meaningfully different content during prerendering versus after interactivity establishes (e.g. show a placeholder chart until a JS charting library initializes), branch on an explicit `_isInteractive` flag set to true only inside `OnAfterRenderAsync(firstRender)`, rather than inferring interactivity from side effects. If using .NET 8+ render modes, be explicit about which render mode this component is declared with (`InteractiveServer`, `InteractiveWebAssembly`, `InteractiveAuto`, or static SSR) since `InteractiveAuto` in particular prerenders, then runs Server, then may switch to WASM after the WASM runtime downloads — a component that assumes a single interop context for its whole lifetime will break under `InteractiveAuto`'s handoff; if this component cannot safely support that handoff, say so explicitly and recommend pinning a specific render mode instead of silently leaving latent bugs.

Check `NavigationManager` usage similarly: reading `NavigationManager.Uri` is safe during prerendering, but relying on browser-only aspects (e.g. `NavigationManager.LocationChanged` firing, or `NavigateTo` with `forceLoad` behaving like a client navigation) is not meaningful until the app is interactive. Add a note in the component (or existing documentation convention for this codebase) stating explicitly that it supports prerendering and what its prerendered placeholder looks like, so future changes don't reintroduce the same class of bug. Validate manually by loading the page fresh (not via client-side navigation, which skips prerendering) and confirming no console/server errors appear before interactivity establishes; add a bUnit test if feasible that renders the component without JS interop configured (simulating prerendering conditions) and asserts it does not throw.
