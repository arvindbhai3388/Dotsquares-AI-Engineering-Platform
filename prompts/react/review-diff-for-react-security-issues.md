# Review a Diff for React-Specific Security Issues

**Category:** React
**Use when:** Before merging a PR that renders user-generated, third-party, or API-sourced content, or as a periodic security pass over a feature area.

## Prompt

Review the diff (read-only pass — report findings with file/line references before proposing any fix) against these React-specific risk categories, and be specific about exploitability rather than flagging every occurrence of a risky-looking API on principle:

**`dangerouslySetInnerHTML`** — flag every usage and trace the HTML string back to its source. If it originates from user input, an API response, or any other content not fully controlled by this codebase, this is a stored/reflected XSS vector: React's default JSX text/attribute interpolation already escapes values automatically, and `dangerouslySetInnerHTML` is the one place that protection is explicitly opted out of. Propose either removing it in favor of plain text rendering, or — if rendering actual rich HTML (e.g. CMS content, a rich-text editor's output) is a genuine requirement — sanitizing the string through a library already vetted for this (e.g. `DOMPurify`) immediately before it's passed in, not sanitized once upstream and then trusted forever after. Confirm the sanitizer's config actually strips `<script>`, inline event handlers (`onerror`, `onclick`), and `javascript:` URLs, not just obvious tags.

**Unsafe URLs and attributes** — flag any `href`, `src`, or `action` built from user/API-supplied strings without validating the scheme, since a `javascript:` URL in an `href` executes on click. Flag `target="_blank"` links to external/user-supplied URLs missing `rel="noopener noreferrer"` (reverse tabnabbing). Flag any use of `iframe src` pointed at user-controlled or unvalidated third-party origins.

**Client-side secrets and trust boundaries** — flag any API key, secret, or credential embedded in client-side code or a `VITE_*`/`NEXT_PUBLIC_*`-prefixed environment variable that gets bundled into the shipped JS, since anything in client-side code (including build-time env vars meant for the browser) is visible to anyone who opens dev tools, regardless of how it's obscured. Confirm anything sensitive stays server-side and is only ever exposed to the client via an authenticated API call. Flag any client-side-only authorization check (hiding a button, disabling a route) presented as if it were a real security boundary — the corresponding ASP.NET Core endpoint must independently enforce the same authorization, since a client-side check is only a UX nicety.

**Storage and exposure of sensitive data** — flag auth tokens or PII stored in `localStorage`/`sessionStorage` (readable by any script that gets injected, i.e. any successful XSS elsewhere becomes a full session-theft vector) versus an httpOnly cookie set by the backend, and flag sensitive data logged to `console.log`/error-reporting tools (e.g. a caught error object that includes a full request body or auth header) in a way that would land in production browser consoles or a client-side error-monitoring service's captured payload.

**Dependency and prop-injection risk** — flag any use of `JSON.parse` on data injected directly into an inline `<script>` tag during server-side rendering without proper escaping (SSR-specific XSS via unescaped `</script>` sequences in serialized state). Flag spreading unvalidated third-party/API response objects directly as props onto components that eventually reach a `dangerouslySetInnerHTML` or URL-attribute sink identified above.

For each confirmed issue, propose the minimal fix (sanitize at the render boundary, validate the URL scheme with an allowlist, move the secret server-side, switch storage mechanism) and flag any fix that would be a larger architectural change (e.g. moving from `localStorage` tokens to httpOnly cookies) as needing separate sign-off rather than folding it into this review's diff. Note which issues, if any, warrant a corresponding regression test (e.g. asserting a component renders a `javascript:` URL as inert/stripped, or that a sanitizer test double confirms a script tag is removed) versus which are process/config fixes with no meaningful unit-test surface.
