# Add Optimistic UI Updates for a Mutation

**Category:** React
**Use when:** A create/update/delete action (e.g. toggling a flag, reordering a list, editing a field) feels sluggish because the UI waits for the API round-trip before reflecting the change.

## Prompt

Before implementing, confirm this mutation is actually a good candidate for optimism: the action should be very likely to succeed, the visible result of "guessing" should be easy to compute client-side, and a failure should be rare enough that a visible revert on error isn't a jarring, frequent experience for users. Propose which specific interactions get the optimistic treatment and which don't (e.g. a simple toggle is a strong candidate; a payment submission generally is not) before implementing, and confirm the rollback UX (does it silently revert, or show an error toast explaining the change didn't stick?).

If this project uses TanStack Query, implement it via the mutation's `onMutate`/`onError`/`onSettled` lifecycle: in `onMutate`, cancel any in-flight queries for the affected key with `queryClient.cancelQueries({ queryKey })` (so a racing background refetch can't overwrite your optimistic write), snapshot the current cache value with `queryClient.getQueryData(queryKey)`, write the optimistic result with `queryClient.setQueryData(queryKey, updater)`, and return the snapshot from `onMutate` so it's available as context; in `onError`, roll back using that snapshot (`queryClient.setQueryData(queryKey, context.previousValue)`); in `onSettled`, invalidate the query so the server's authoritative state eventually reconciles regardless of success or failure. If this project uses manual `useState` instead, apply the equivalent pattern by hand: capture the previous value before mutating local state, apply the optimistic value immediately, then revert to the captured previous value in the catch block if the API call fails.

Make sure the optimistic value is computed the same way the server would compute it wherever that matters (e.g. a computed total, a sort order) so the eventual server response doesn't visibly "jump" when it arrives — if the server could plausibly compute a different result than the client's guess (e.g. server-side validation adjusts a value), don't just optimistically show the client's guess as final; consider a subtler in-flight indicator instead. Disable the triggering control (or debounce rapid repeated triggers, e.g. double-clicking a toggle) so concurrent optimistic writes to the same key don't race each other and produce an inconsistent rollback.

Write tests covering: the optimistic value appears immediately in the render before the mocked API call resolves, a successful response leaves the optimistic value in place (or reconciles cleanly with the real response), and a failed/rejected API call rolls the UI back to the pre-mutation value and surfaces an error indication — using fake timers or manually controlling the mocked promise's resolution timing to assert the intermediate optimistic state is actually visible, not just the before/after states.
