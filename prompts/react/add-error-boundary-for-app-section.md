# Set Up Error Boundaries for a Section of the App

**Category:** React
**Use when:** An unhandled render error in one part of the UI currently blanks out or crashes the entire app instead of being contained.

## Prompt

Before implementing, identify the natural boundary granularity for this app — typically one boundary near the app root as a last-resort catch-all, plus finer-grained boundaries around independently-failing sections (a route, a widget/panel that renders third-party or less-trusted data, a chart, a rich third-party embed) so one section's crash doesn't take down unrelated UI around it. Propose the specific boundary placements before implementing, since a boundary that's too coarse (only at the root) makes every error a full-page blank, while one boundary per tiny component adds noise without benefit.

Error boundaries must currently be implemented as a class component (`static getDerivedStateFromError` to render a fallback, `componentDidCatch` to log/report) since there is still no hook equivalent for this exact lifecycle in React — check whether this project already has a shared `ErrorBoundary` component or a library dependency (e.g. `react-error-boundary`, which provides `ErrorBoundary`/`useErrorBoundary` as a function-friendly wrapper) before writing a new class from scratch. If using `react-error-boundary`, use its `FallbackComponent`/`fallbackRender` prop for the recovery UI and its `onReset`/`resetKeys` support so a boundary can be reset (e.g. when the user navigates away and back, or clicks "try again") without a full page reload.

Be explicit about what an error boundary does *not* catch, since this is the most common misunderstanding: it does not catch errors in event handlers (those need a plain `try`/`catch` at the call site), errors in asynchronous code (`setTimeout` callbacks, promise rejections — handle with `try`/`catch`/`.catch`), errors during server-side rendering, or errors thrown in the boundary's own fallback rendering. Do not present an error boundary as a substitute for proper error handling in async data-fetching paths (see this category's loading/error-states prompt for that).

Design the fallback UI per boundary to be genuinely useful for its scope — a route-level boundary's fallback might offer "reload this page" or a link back to a safe route; a widget-level boundary's fallback should be small and not imply the whole app is broken. Report caught errors to this project's existing logging/monitoring setup from `componentDidCatch`/`onError`, not just `console.error`, but never include sensitive data (auth tokens, PII from the failed render's props/state) in what gets logged. If this app also uses lazy-loaded routes (see this category's code-splitting prompt), make sure the relevant boundary also distinguishes a chunk-load failure (prompt for a reload) from a genuine render error.

Write tests that intentionally throw from a child component (a small test-only component that throws in render, or `React.createElement` of one) and assert: the fallback UI renders instead of the app crashing, the reset action (if implemented) successfully re-renders the children after the underlying condition is fixed, and the error-reporting call fired with the expected error. Suppress React's expected console.error noise for these specific tests rather than letting it obscure real failures elsewhere in the suite.
