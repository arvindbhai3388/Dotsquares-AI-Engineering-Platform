# Set Up an Auth Token Interceptor for API Calls

**Category:** React
**Use when:** API calls to the ASP.NET Core backend need a bearer token attached automatically, or 401 responses aren't being handled consistently across the app.

## Prompt

Before implementing, identify the current HTTP client setup (a shared `axios` instance, native `fetch` wrapper, or the client generated for TanStack Query) and where the auth token currently lives (memory, `localStorage`/`sessionStorage`, an httpOnly cookie set by the backend, or a state manager) — propose the interceptor design against that, since the correct pattern differs meaningfully by token storage: storing a JWT in `localStorage` is readable by any injected script (XSS risk), while an httpOnly cookie needs `credentials: 'include'`/`withCredentials: true` instead of a manually attached header. Flag if the current storage choice looks like a security concern, but don't silently change it as a side effect of this task — call it out and confirm before switching storage strategy.

Implement the outgoing side as a single interceptor/wrapper, not per-call code: for `axios`, an `axios.interceptors.request.use` that reads the current token (from memory/context, not by re-reading storage on every call if it's already held in a more current source of truth) and sets the `Authorization: Bearer <token>` header only if a token is present; for `fetch`, a thin wrapper function used by every API call site rather than duplicating the header-attach logic. Ensure the token is read fresh at call time, not captured once at module load — a stale closure here means a refreshed token never actually gets used (see this category's stale-closure prompt if that pattern shows up).

Implement the incoming side to handle 401s consistently: on `axios`, a response interceptor's error handler; on `fetch`, a check in the shared wrapper. If this app supports refresh tokens, attempt exactly one silent refresh-and-retry per original request (using a shared in-flight refresh promise so concurrent 401s from multiple simultaneous requests don't each trigger their own refresh call — a classic thundering-herd bug), and only redirect to login if the refresh itself fails. If there's no refresh flow, redirect to login (or dispatch a logout action) directly on 401, and clear any stored token/auth state to avoid retrying with a known-dead token. Never retry the same request in an infinite loop — cap retries at one refresh attempt per request, and mark retried requests to prevent re-entering the interceptor.

Never log the token value itself, even at debug level, and never place it in a URL query string. Write tests (mocking the HTTP client, e.g. with `msw` or an axios mock) covering: a request gets the header attached when a token exists, no `Authorization` header is sent when there's no token, a 401 triggers the refresh-and-retry path exactly once for concurrent requests if refresh is supported, and a failed refresh triggers logout/redirect exactly once (not once per concurrent failed request).
