# Debug an ExpressionChangedAfterItHasBeenCheckedError

**Category:** Angular
**Use when:** The app throws `NG0100: ExpressionChangedAfterItHasBeenCheckedError` in development mode, usually after a recent template/lifecycle-hook change.

## Prompt

Read the full error message first — it names the property, the previous value, and the current value Angular detected changing between checks — and use that to locate the exact binding before searching further. Then find the source of the second-pass change by checking, in order of likelihood: a parent component mutating a value the child reads as an `@Input()`/signal input during the parent's own `ngAfterViewInit`/`ngAfterContentInit` (these hooks run after the child has already been checked once this cycle, so any state change here is exactly one tick too late); a child calling a parent's callback or mutating a shared/injected service's state from within its own `ngOnInit`/`ngAfterViewInit`, which changes a value the parent template already rendered this pass; a getter or method called directly in a template expression (`{{ getStatus() }}`, `*ngIf="isValid()"`) that returns a different value on its second invocation within the same cycle because it reads mutable state that something else in the tree just changed; or a `@ViewChild`/`@ContentChild` query result used to set a bound property inside `ngAfterViewInit` without deferring it.

Report which of these is the actual cause here with the specific file/line evidence (which component set what, when, that the error's "previous vs current" values match) before proposing a fix — don't guess and immediately patch the symptom by wrapping the offending call in `setTimeout`, which suppresses the error without fixing the underlying timing bug and can introduce a visible flash of stale content.

Fix based on the actual cause: if a parent needs to react to a child's rendered output, move the update out of `ngAfterViewInit` and into a `computed()` signal the template reads directly (recomputation naturally happens in the same cycle without a stale-then-corrected render), or use `Promise.resolve().then(() => ...)`/schedule the update for the next macrotask only if a signal-based restructure genuinely isn't feasible here — and explain why `computed()` wasn't viable if you fall back to this. If the cause is a template calling an impure method, convert it to a `computed()` signal or a pure `Pipe` so it only re-evaluates when its actual inputs change, which both fixes the error and the redundant-recalculation performance cost together.

After the fix, reproduce the original triggering interaction and confirm the error no longer appears in the console (development mode, since this check is a dev-mode-only assertion and won't reproduce in a production build) — verifying in dev mode specifically matters, since a fix that only "works" because production strips the check isn't actually a fix. Add a test that exercises the exact interaction sequence that triggered the error if it's driven by a specific user action, so a regression would be caught by the suite rather than only by a developer's console.
