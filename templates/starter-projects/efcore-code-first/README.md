# Starter Scaffold — Entity Framework Core (Code-First)

> Template outline for bootstrapping a new EF Core Code-First data layer. This is a
> folder-structure and setup guide, not a working demo — see `demos/` for a runnable example.
> Note: some client repos on this platform use **EF6 Database-First** or raw ADO.NET instead
> (e.g. legacy .NET Framework apps) — check the client's `CLAUDE.md` §4.6 before assuming
> Code-First EF Core applies.

## Recommended Folder Structure

```text
<ProjectName>.Data/
├── <ProjectName>.Data.csproj
├── <Context>DbContext.cs             # One DbContext per bounded context, not one god-context
├── Entities/
│   └── <Entity>.cs                   # POCOs — no EF-specific attributes beyond simple annotations
├── Configurations/
│   └── <Entity>Configuration.cs      # IEntityTypeConfiguration<T> — one per entity, applied via ApplyConfigurationsFromAssembly
├── Migrations/                       # Generated by `dotnet ef migrations add` — do not hand-edit generated Up/Down beyond review
├── Repositories/                     # Only if the project convention uses repositories over DbContext directly
│   ├── I<Entity>Repository.cs
│   └── <Entity>Repository.cs
├── Seed/
│   └── <Context>SeedData.cs          # Idempotent seed logic, no production secrets/PII
└── Extensions/
    └── ServiceCollectionExtensions.cs  # AddDbContext<T> registration, connection string binding
```

## Key NuGet Packages

| Package | Purpose |
|---|---|
| `Microsoft.EntityFrameworkCore` | Core EF Core |
| `Microsoft.EntityFrameworkCore.SqlServer` | SQL Server provider (swap per client's actual DB) |
| `Microsoft.EntityFrameworkCore.Design` | Design-time tooling for `dotnet ef` commands |
| `Microsoft.EntityFrameworkCore.Tools` | `dotnet ef migrations`/`database update` CLI support |

Never reference `Microsoft.EntityFrameworkCore` in a repo that has standardized on EF6 or raw
ADO.NET — confirm which data-access approach the target project actually uses first.

## First Things to Configure

1. Register `DbContext` as **scoped** (the EF Core default via `AddDbContext<T>`) — never
   share an instance across concurrent operations or promote it to singleton.
2. Bind the connection string from configuration (`IOptions<T>` or
   `builder.Configuration.GetConnectionString(...)`) — never hardcode it, and never commit a
   real one to `appsettings.json`.
3. Use `IEntityTypeConfiguration<T>` per entity instead of one large
   `OnModelCreating` method, applied via `modelBuilder.ApplyConfigurationsFromAssembly(...)`.
4. Use `AsNoTracking()` for read-only queries; reserve tracked queries for entities that will
   actually be updated in the same context instance.
5. Set up the migration workflow explicitly: `dotnet ef migrations add <Name>` reviewed
   (Up/Down inspected) before `dotnet ef database update` is run against any shared
   environment.
6. Set up the paired test project (xUnit + EF Core's in-memory or SQLite provider for unit
   tests, or a real SQL Server test container for integration tests — match the client's
   convention) before writing repository/query logic (Test-First).
